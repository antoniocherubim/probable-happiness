# DX-08A1 — Relatório Cursor seguro na extensão de iterações

Status: implementada (aguarda revisão).

Base obrigatória: `wip/dx-08a-review-7`.

Próxima task: [DX-08A2](DX-08A2.md).

## Contexto

O review 7 da DX-08A reproduziu uma extensão de orçamento usando
`cursor-<iteration>.json` com conteúdo `not json` e modo `0644`.
`_authorize_iteration_extension_locked()` verificava apenas tipo e tamanho do
arquivo antes de promover o evento crítico.

## Objetivo único

Fazer a autorização de iterações aceitar somente um relatório Cursor Agent
privado, lido sem seguir links e válido segundo o envelope de produção já
usado por `snapshot.py`.

## Escopo obrigatório

1. Substituir a validação superficial de `cursor-<iteration>.json` em
   `_authorize_iteration_extension_locked()` pela API segura comum.
2. Reutilizar ou extrair o validador existente do envelope Cursor Agent; não
   criar um segundo contrato divergente.
3. Recusar antes de qualquer mutação:
   - JSON ausente, vazio, truncado ou malformado;
   - schema/contrato futuro ou campos ausentes, extras ou de tipo inválido;
   - symlink, hard link, arquivo não regular ou troca de inode;
   - modo diferente de `0600` e owner inesperado.
4. Preservar a autorização normal com um envelope real de
   `cursor --output-format json`.
5. Ajustar `ROADMAP.md` e esta task apenas com a garantia específica provada;
   DX-08 e M1 continuam abertos.

## Limite de mudança

Arquivos de produção permitidos:

- `scripts/agents/dx/runstate.py`;
- `scripts/agents/dx/snapshot.py`, somente para compartilhar o contrato.

Testes em `tests/unit/test_agent_dx08a.py` e documentação citada acima.
Não alterar runtime, locks, transactions, migration, rollback ou outros fluxos
de reports. Não fazer refatorações adjacentes.

## Critérios de aceite

1. Todos os relatórios inseguros listados são recusados.
2. Na recusa, budget, status, audit, journal e diretório permanecem
   byte-a-byte inalterados (com `.resume.lock` pré-presente como cerca).
3. Um envelope de produção válido ainda autoriza a extensão.
4. A suíte completa e as validações estáticas passam.

## Implementação

- `_require_private_executor_envelope()` em `runstate.py` lê
  `cursor-<iteration>.json` via API segura (`secure_lstat_regular` /
  `secure_read_json`, `require_private=True`, containment no run dir), exige
  modo **exatamente** `0600` (além de `require_private`, que sozinho ainda
  aceitaria `0400`/`0500`/`0700`) e valida o envelope com
  `validate_executor_envelope` **antes** de qualquer mutação de
  budget/status/audit/journal.
- `validate_executor_envelope` tornou-se API pública em `snapshot.py` (mesmo
  contrato de `prepare_review_artifacts`); resume reutiliza o mesmo validador
  em `_validate_resume_report_contract` — sem segundo schema divergente.
- Recusas cobertas: JSON malformado/truncado/vazio, fixture sintético
  `{"summary":…}`, campos extras/ausentes/tipos inválidos, symlink, hard link,
  owner inesperado, modos `0644`/`0666`/`0400`/`0500`/`0700`.
- Pré-condição de invariância na recusa: `.resume.lock` (cerca de
  concorrência da autorização) já presente e `0600`. Sob essa pré-condição, o
  snapshot completo do diretório — incluindo a entrada do lock — permanece
  byte-a-byte inalterado; a cerca não é enfraquecida.

## Riscos residuais

- DX-08A2 (status/heartbeat em diretório seguro) e DX-08B (migration/backup/
  rollback) permanecem abertos; DX-08 e M1 não estão fechados.
- Nenhum hash de commit de entrega nem URL de branch foram publicados aqui.
- Owner inesperado na matriz de authorize é exercitado via falha fechada da
  checagem de owner da API comum no caminho de `cursor-*.json` (a comparação
  uid real vs `geteuid` continua coberta nos testes de `persist`); troca de
  inode no open permanece na API segura comum, sem fault injection dedicado
  nesta fatia.
- Se `.resume.lock` estiver ausente na primeira chamada a
  `authorize_iteration_extension`, o protocolo de lock pode criar essa entrada
  `0600` (cerca de concorrência); isso não muta budget/status/audit/journal.
  A garantia byte-a-byte do diretório na recusa é provada com a cerca já
  presente (pré-condição documentada acima).
- Baseline de ameaça inalterado: mesmo UID é confiável; root/peer hostil sob o
  mesmo UID permanece fora de escopo.
