# PS-01 — Scope systemd e encerramento de descendentes

Status: aceita para o baseline pessoal após revisão manual.

Base: `wip/dx-08a1-review-2`.

Política de review: somente defeito que viole diretamente o objetivo ou aceite
abaixo pode retornar `CHANGES_REQUESTED`. Proteção contra mesmo UID, quotas e
outros itens fora de escopo devem ser backlog não bloqueante.

## Objetivo único

Executar cada fase do agente em um scope systemd de usuário e garantir que o
scope esteja vazio ao terminar, inclusive quando um descendente cria nova
sessão ou quando o sandbox do Cursor se torna órfão.

## Escopo

- backend único `systemd --user`, disponível no host pessoal;
- nome de unidade derivado de run/fase/iteração sem conteúdo sensível;
- iniciar a fase no scope, registrar sua unidade no heartbeat e manter o
  comportamento de stdout/stderr atual;
- em sucesso, erro, timeout, sinal ou falha de heartbeat, parar a unidade,
  aguardar estado inativo e confirmar que seu cgroup ficou vazio;
- recusar o start se o scope não puder ser criado; não oferecer fallback
  silencioso para process group;
- alterar somente runtime, invocação da fase, testes focados e documentação
  desta task.

Não adicionar quotas de memória/CPU/processos, migration, rollback, reports,
retenção geral ou proteção contra outro processo deliberado com o mesmo UID.

## Aceite

- fase normal mantém resultado e logs atuais;
- descendente com `setsid` e wrappers do sandbox são encerrados;
- saída 0 do comando principal com descendente sobrevivente ainda para o
  scope, preserva logs/result e deixa a unidade inativa/vazia;
- erro injetado após spawn (inclusive query `systemctl` antes do retorno de
  `start_scoped_popen`, e antes dos signal handlers em `supervise_command`)
  deixa a unidade inativa e o cgroup vazio;
- falhas de `systemctl` show/stop e leitura de cgroup falham fechado;
- população recursiva do cgroup (filho aninhado / `cgroup.events`) é
  verificada;
- falha de criação de unidade transitória (evidência positiva no stderr do
  `systemd-run`) vira `SystemdScopeError`; exit nonzero de comando curto
  legítimo — inclusive `/bin/false` sob race com `--collect` — permanece
  falha de comando;
- SIGINT, SIGTERM e SIGHUP disparam cleanup após a instalação dos handlers;
- o teste de integração com systemd de usuário é executado, não apenas skipped;
- nenhuma operação Git ou de rede é adicionada;
- suíte completa e checks estáticos passam.

## Implementação

- `scripts/agents/dx/systemd_scope.py`: cria scope transitório via
  `systemd-run --user --scope --collect --property=Delegate=yes`, para a
  unidade com `systemctl --user stop`, aguarda estado inativo e exige cgroup
  recursive-empty via `cgroup.events` (`populated`). Query/stop/I/O de cgroup
  distinguem unidade ausente de falha de barramento e falham fechado.
  `start_scoped_popen` é dono do reap até retornar o `Popen`: qualquer
  exceção pós-`Popen` (incl. falha de `_show_unit_properties`) para a
  unidade, mata o wrapper/sessão e esvazia o cgroup antes de propagar.
  Criação transitória recusada exige evidência positiva no stderr
  (`Failed to start transient` etc.); ausência de unidade após `--collect`
  com exit nonzero sem essa evidência é tratada como resultado do comando.
- `scripts/agents/dx/runtime.py`: `supervise_command` deixa de usar
  `killpg`/process group como isolamento; heartbeat/result passam a registrar
  `systemd_unit` e `process_group=null`. Após retorno bem-sucedido de
  `start_scoped_popen`, qualquer exceção pós-spawn e o exit do comando
  (sucesso incluído) param e esvaziam a unidade.
- Start falha fechado (`SystemdScopeError`) se o manager de usuário estiver
  indisponível ou o scope não ficar ativo enquanto o filho ainda corre; a CLI
  propaga o erro sem cair em process group.
- Nome da unidade: `agent-loop-<run>-<phase>-<iteration>.scope`, sanitizado.
- `systemd_unit` é opcional nos contratos estritos de resultado: runs legados
  continuam legíveis e novos resultados preservam a identificação do scope.
- Respostas bem-sucedidas porém incompletas de `systemctl show` falham fechado,
  em vez de serem confundidas com unidade ausente.

## Decisão final da revisão

A terceira revisão ainda retornou `CHANGES_REQUESTED`. Os dois defeitos que
afetavam diretamente o uso pessoal foram corrigidos manualmente: compatibilidade
do novo campo `systemd_unit` com os contratos de artefato e tratamento
fail-closed de respostas incompletas do `systemctl show`.

Os demais findings são hardening para concorrência/falha de infraestrutura e
foram aceitos como restrições operacionais: executar somente um `agent-loop`
por vez, não interromper manualmente durante os primeiros instantes do start e
considerar indisponibilidade persistente do `systemd --user` uma condição de
parada. Esta aceitação do operador não equivale a aprovação automática do
reviewer.

## Evidência de teste

Executado neste host com `systemd --user` em estado `degraded` (aceitável para
scopes transitórios), fora do sandbox (bus de usuário alcançável):

```text
pytest -q tests/unit/test_agent_ps01.py
→ 22 passed

pytest tests/unit -q
→ 483 passed

python3 -m compileall -q scripts/agents/dx
git diff --check
→ ok
```

Cobertura PS-01: contrato novo e legado de artefatos; resposta incompleta de
`systemctl show`; fase normal com logs/unit no heartbeat; timeout com filho
`setsid`; exit 0 com descendente `setsid` sobrevivente (logs/result
preservados, unidade vazia); órfão double-fork estilo sandbox; cgroup filho
aninhado; falha de status/heartbeat após spawn; exceção antes dos signal
handlers; falha injetada de `_show_unit_properties` pós-Popen (wrapper e
cgroup reaped); falhas de systemctl/cgroup fail-closed; criação transitória
recusada vs comando curto exit nonzero e regressão repetida de `/bin/false`;
SIGINT/SIGTERM/SIGHUP; integração real lendo `/proc/self/cgroup`. Nenhum skip.

## Riscos residuais / backlog

- processo do mesmo UID que migre deliberadamente para outro cgroup/slice ainda
  pode escapar (fora do modelo pessoal);
- quotas MemoryMax/TasksMax/CPU e limites de saída ficam para PS-02/PS-03 e
  DX-09;
- manager `systemd --user` offline impede qualquer fase (falha fechada, sem
  degradê silencioso);
- somente um loop deve estar ativo por vez: nomes de unidade não incluem a
  identidade do projeto e podem colidir entre projetos com o mesmo run id;
- um sinal externo durante a pequena janela anterior à instalação dos handlers
  pode exigir verificação manual de órfãos;
- falha persistente do próprio `systemctl` pode impedir a confirmação de
  cleanup; nesse caso, não retomar até restaurar o manager e conferir o scope;
- falha de criação transitória cujo stderr não case o detector conhecido pode
  aparecer como falha ordinária de comando (exit nonzero) em vez de
  `SystemdScopeError`;
- resume ainda não limpa metadados de unidade antiga de crash/reboot (DX-09).
